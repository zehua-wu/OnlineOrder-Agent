# 用 OnlineOrder Agent V2 回答工程面试

这份材料适合准备 Agent/SDE 项目深挖。HR 初筛通常看你能否清楚表达自己的贡献与证据；技术面会追问状态、一致性、失败模式和指标。任何文档都不能保证通过某家公司的面试。有效准备方式是运行项目、改动一个边界并解释测试结果，而不是背框架名。

回答时区分三件事：本分支已经实现什么、用什么测试证明、哪些能力还没有做到。以下答案都基于当前代码。

## 1. 先用两分钟介绍项目

“我在现有点餐系统外增加了一个 FastAPI Agent Harness。模型通过 Qwen/DeepSeek 的兼容 API 识别意图和提出工具调用；Harness 管理多轮 Session、偏好记忆、候选位置、参数验证和工具执行。商品与购物车仍由 Spring 决定。

我重点解决了多轮条件丢失和写操作可靠性：把筛选和已选商品存成结构化状态，而非只依赖聊天历史；购物车添加分为准备和用户确认两轮。审查源码发现现有 add API 是累加且没有幂等键，因此实现请求与动作两层日志，单 action 不自动重发。超时后停止后续写入，让用户查看购物车并显式核对。

我用 Mock 后端、假模型、SDK wire Mock 和共享 Redis 模拟验证正常与异常路径；评测分别统计工具参数、执行、任务、召回和延迟。Mock 分数只说明回归，真实平台质量和线上性能还需要独立测试集与真实环境验证。”

不要说“用了 memory、ReAct、RAG 所以可靠”。对方接下来会问这些词到底对应哪段状态和执行代码。

## 2. Memory 与检索：常见问题和继续追问

### Q1：长短期记忆分别是什么，为什么不把所有对话塞进 prompt？

短期是 Session 的近期消息、旧用户引用和工作状态；长期是 Spring 保存的跨 Session 稳定偏好。原始对话无界增长会增加费用、延迟、信息冲突和注入面。V2 保留近期完整轮次，老用户原话有界压缩；商品 ID、筛选、pending_action 不依赖摘要恢复。

继续追问“摘要丢了用户预算怎么办”：预算应进入 `state.search.max_price`。如果只在自由文本出现却未被模型转成状态，仍可能丢失；需要条件保持测试，不能声称压缩永不丢信息。

### Q2：为什么短期记忆不就是 messages？

“第二个”依赖有序候选；“还是15美元以内”依赖有效筛选；“确认”依赖带身份与期限的 action。这些是结构化工作记忆。messages 保存沟通，state 保存可校验引用和工作流。长期口味也不能承担 cart 的事实状态。

### Q3：什么写入长期记忆，如何避免污染？

普通单次点餐不写；稳定偏好表达才触发独立抽取。返回值经过 schema、类别、原文 evidence 和条数限制，DELETE 只处理已知 key。当前门控是保守启发式，仍可能误归纳；没有声称 evidence 子串就是语义证明。

追问“用户说今天想吃辣，会改偏好吗”：抽取提示明确排除今天/这次，普通表达不触发门控；应加入带稳定信号又含当天例外的对抗样例，测实际误写率。

### Q4：历史偏好与当前指令冲突怎么办？

当前明确需求优先。记忆只填未指定偏好，不能强行覆盖“这次不限预算”。结构化增量通过 clear_filters 或 start_new_search 管理。过敏属于提醒约束，遇到冲突应澄清；后端没有过敏原合同，不能给出过敏安全保证。

### Q5：长期记忆怎么跨用户隔离？

Agent 通过 users/me 得到稳定用户 ID，Session/journal 按这个 ID 绑定；Spring memory API 再独立从 JWT 派生 user_id。模型、请求 body 都不能选 user_id。Token 刷新不会换用户身份。跨用户 Session 403、action 查询 404 都有测试。

### Q6：检索用 embedding 了吗，召回率怎么定义？

当前没有 embedding。菜单真实 API 是 SQL 条件+子串匹配；偏好检索是候选内词重合排序并优先保留安全约束。Recall@k = gold 中被前 k 个结果命中的数量 / gold 总数；菜单与记忆分别报告。

继续追问“为什么没上向量库”：菜单结构小、条件严格、后端没有向量接口。先建立可解释基线与数据集。规模增长后可引入关键词+向量候选、结构过滤和 rerank，但要证明召回收益与成本；不能为架构图添加并不存在的能力。

### Q7：最近50条记忆之外的过敏信息怎么办？

当前可能漏掉，这是明确限制。候选内保留所有安全约束不能保证候选外不漏。真实生产应把长期安全约束和可淘汰偏好分开存取，或获得全量/专门接口，并让用户复核。受本任务不修改 Backend 的约束，V2 不谎称已解决。

### Q8：为什么没有用 LLM 生成滚动摘要？

生成式摘要可能把模型推测固化成事实，并额外消耗 token。当前采用旧用户原话的有界引用，关键条件结构化保存。其语义覆盖能力有限，但容易解释与测试；下一步可用有证据的摘要并评估事实保持率。

## 3. Session 与多轮状态

### Q9：Session ID、user ID、request ID、action ID 的区别？

Session 标识一段对话；user 是稳定认证身份；request 标识一次客户端意图及其重试；action 标识一项待执行的购物车增量。一个用户有多个 Session，一个 Session 有多个 request，一个 action 可被不同 request 重复确认但不会重复提交。

### Q10：Session 放哪里，多久过期？

开发使用内存序列化副本，生产配置要求 Redis 单文档+TTL，默认4小时；action/request journal 默认7天。显式 sessionId 不存在返回404，不自动创建新空状态。日志保留期不小于 Session 期限，但仍受存储丢失和 eviction 影响。

### Q11：用户两个标签页同时聊天会怎么样？

Agent 按用户上锁，两个 Session 也串行，避免同时操作同一 cart 或反序写偏好。内存锁只支持一个进程，Redis 锁支持多个 worker。原 UI 直接调用 Spring 不受 Agent 锁控制，因此不能用数量差推断 UNKNOWN action 成功。

追问“锁的吞吐代价”：同用户长模型等待会阻塞其他 Agent 请求；可以未来把只读 Session 与 cart 写锁分开，但必须明确依赖与写屏障，不能只为 QPS 去掉锁。

### Q12：为什么保存 revision，但没有 CAS？

当前 revision 是完成轮次观察值，依赖用户互斥保证正常路径顺序，**不是**乐观并发版本或 fencing token。Redis 单 SET 防止半份 JSON，不自动防止两个无锁写覆盖。如果要求更强并发，应增加 CAS/fencing 和存储级验证。

### Q13：跨轮指代如何避免选错？

候选的 position→真实 menu UUID 映射由应用保存。选择/添加通过 position 定位；成功新搜索或菜单浏览替换候选并撤销旧选择/待确认动作。引用超过15分钟需要刷新。位置是对最后结果集的引用，不是全库永久编号。

## 4. Tool Calling 与 Orchestration

### Q14：这个 Agent 的 loop 是什么，停止条件有哪些？

模型输出工具请求 → executor 校验执行 → 状态 checkpoint → tool result 回送 → 下次模型调用。得到非空最终文本结束；准备添加时由应用直接返回确认提示。5个工具上限、75秒总时限、上下文预算和重复签名检测限制失控；超限返回降级状态并保留已完成结果。

### Q15：为什么不是直接让模型“自主执行所有步骤”？

模型能解释自然语言，但不能可靠维护授权和事务。模型不接触 JWT，不决定 user_id，不写数据库，不确认自己的副作用。程序将“可提出的操作”与“允许现在执行的操作”分开。现有工具集合本身就是最小能力边界。

### Q16：参数验证只靠 JSON Schema 够吗？

不够。schema 验证类型、范围和多余字段；语义验证还要确认 position 存在、ID 来自真实结果、快照未过期、筛选合并后范围合法、pending action 未过期且用户确认的是同一个动作。数量字符串、bool、负数、伪造 confirmed 字段都有拒绝测试。

### Q17：为什么选择和加入购物车分两个工具？

“第二个不错”表达偏好，并没有明确授权修改 cart。select 只记录状态；add_to_cart 也只准备，下一条用户明确确认才写。这个设计额外增加一次交互，换来可审查参数和明确副作用边界。

### Q18：模型返回多个 tool calls 能并行吗？

当前顺序执行，因为状态依赖常见，便于定义错误与部分成功。可以将被证明独立的只读工具并行，但搜索与选择、选择与添加有依赖。并行工具执行能力不是越多越好，先看任务图与状态一致性。

### Q19：Qwen 与 DeepSeek 的封装具体做了什么？

统一 LanguageModel/ModelTurn/ToolCall；使用 Chat Completions function 格式，将 developer role 转成兼容的 system role，保存 assistant tool_calls，再回送相同 ID 的 role=tool 消息。避免发送不通用 strict/parallel 参数，依然本地校验。Key/BaseURL/model/超时/重试都从环境配置读取，SDK wire 有 Mock 测试，真实 Key 还未验证。

### Q20：怎么对付 tool result 里的 prompt injection？

把菜单、记忆和旧引用标为不可信数据；输出校验与工具白名单不依赖 prompt；模型没有确认工具和凭据，写动作必须后续用户通过程序路径确认。这样可以限制副作用，但不能保证模型所有自然语言解释都不受影响。真实对抗集仍需测真实性与误选项。

## 5. 错误、重试、幂等与恢复

### Q21：为什么 add_to_cart 不能用重试框架重试三次？

审查真实 CartService 发现它会 increaseQuantity，且 Controller 不支持幂等键。超时可能是“后端提交了，响应没收到”。重试会多加。V2 对读接口有限重试，对 cart POST 单次发送并记录 UNKNOWN；这比盲目提升表面成功率更符合业务语义。

### Q22：你说实现幂等，能保证 exactly-once 吗？

不能。requestId 去重 HTTP 意图；actionId+NX 日志避免同 action 再次派发。但 Agent 日志与 Spring 事务不原子，仍有提交后未记成功的窗口，所以停止重试并人工核对。更强方案是未来把 idempotency key、请求 hash、业务修改及回执放入 Spring 同一数据库事务。

追问“那现在是 at-most-once 还是 at-least-once”：在日志保留、未丢失和已知 action 的范围内，设计目标是保守的至多一次派发；可能一次也没发送却被标 STARTED，牺牲了可用性。不能把有限条件结论扩大到 Redis 丢失或原 UI 请求。

### Q23：确认成功后保存 Session 失败会怎么样？

发送前已保存 STARTED action 与屏障。成功结果若已落日志，重复确认返回回执；若结果没落日志，仍是 STARTED，不会自动再 POST。测试注入“后端已提交、Redis 写成功记录失败”，验证第二个请求没有第二次提交。

### Q24：为什么查看 cart 后不自动判断之前是否成功？

购物车数量变化可能来自原 UI、另一个客户端或其他合法 action，读取也不提供操作因果。单纯数量差不是幂等凭据。acknowledge 只表示用户核对后允许继续，不证明原动作成功或失败，也不重发旧操作。

### Q25：锁到期或服务暂停怎么办？

Redis lock 有租约，配置比整轮时限长30秒；NX action 日志是第二道防线。长暂停、分区和 failover 仍不能等价于数据库 fencing。当前测试用 fakeredis 验证共享锁语义，未证明真实集群故障一致性；需要混沌测试与更强后端幂等。

### Q26：错误如何分类，什么时候能继续？

参数错给模型安全反馈并允许有界纠正；401/403 不重试；读429/5xx有限退避；写超时/5xx/坏成功响应变UNKNOWN；确认过期/请求ID冲突返回409；Session过期404；存储不可用503并阻止无日志写入。普通模型中断返回degraded并保存已有工具结果。

## 6. 评价、性能和规模化

### Q27：Tool Calling 成功率高，为什么任务完成率仍可能低？

工具参数合法、HTTP成功不代表调用了正确工具、保持了全部条件或达到用户目标。比如搜索成功却丢失预算。V2 分别统计 schema 合法、工具序列、筛选语义、工具ok和最终状态；task completion 从后端 cart/state/gold 判断，不靠回答中的“已完成”。

### Q28：离线8/8能说明什么？

只说明这个合成回归集符合预期，其中6个业务任务与2个安全场景分开报告。样本小且部分表达与 mock policy 对齐，不能估计真实分布。6/6业务任务的 Wilson 下界约61.0%，也不能无条件用于重复非独立样本。应扩充独立真实模型测试集并按任务类型分层。

### Q29：Recall、precision、MRR 应该分别看什么？

Recall关注相关项是否被漏；precision关注返回噪声；MRR关注首个正确结果的位置。菜单严格条件可先过滤再排；长期偏好还要看候选检索是否先丢掉关键约束。当前实现只有小型 recall smoke，不能声称复杂 RAG 已达标。

### Q30：怎么优化性能，有没有 p95/QPS 的数字？

没有真实平台数字。当前内部指标不包含鉴权/锁等待，Mock 毫秒级不能当线上延迟。先用真实 tracing 分出模型轮数、token、读工具、重试、记忆和存储，再减少无用抽取、重复查询和长 tool output。确认分支直接执行程序逻辑，不再调用LLM。真实压测需报告并发、硬件、任务分布、错误率和费用。

### Q31：用户量扩大后先改哪一块？

先看指标瓶颈：用户串行排队、provider配额、连接池、Redis日志容量或检索候选上限。动作日志不能随意 LRU 淘汰；可能需持久操作表与归档。记忆需要独立安全约束、索引与版本。引入消息队列不能自动解决幂等，异步任务也要有可查询状态和去重键。

### Q32：为什么没有上 LangGraph、向量库、多Agent？

当前核心是明确状态和真实接口可靠性，小规模显式循环更容易审查和测试。框架可帮助长运行图、checkpoint与可视化，但不会自动提供业务幂等或安全授权。若要引入，应以分支复杂度、恢复需求和测得收益说明原因，而不是把组件数量当技术深度。

## 7. 面试前亲手做的练习

1. 跑完整演示，逐轮对照 Session 文档，解释“为什么这个字段需要程序管理”。
2. 把条件清除和新搜索各试一次，查看有效筛选与候选是否正确更新。
3. 运行 unknown-write 和 Redis 双 worker 测试，说出每个崩溃窗口的恢复方式。
4. 拿到 Key 后跑 configured 评测，挑三个失败样例归因：模型理解、工具选择、参数合并、服务失败还是标签过严。
5. 写下你测得的真实数字及样本/环境；没测过的数字就说没测过，并给出下一步测法。

项目的说服力来自你能解释边界、复现故障、提出有证据的改进，而不是承诺系统永远不会出错。
